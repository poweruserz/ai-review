# ai-review

Reusable GitHub Actions workflow that puts every pull request in poweruserz's repositories through two AI reviewers.

1. **Codex** (the ChatGPT Codex Connector app) runs its code review and security review on every push. It is configured in chatgpt.com/settings/code-review, not here.
2. **Claude** (Opus 5.5 at max effort, on the owner's subscription through a `claude setup-token` token) reviews the same head through [claude-code-action](https://github.com/anthropics/claude-code-action) for correctness and security. It gets Read plus grep and glob from [`scripts/search-mcp.mjs`](scripts/search-mcp.mjs), a read-only MCP server over git with no shell, because native Claude Code builds have no Grep or Glob. The diff and the review rules are taken from the base commit's point of view: `git --attr-source` keeps a `.gitattributes` line the pull request adds from showing its own changes as binary, and `.ai-review.rules` holds the base branch's `AGENTS.md` files (the prompt follows their `## Code Review Rules`), so a pull request cannot rewrite the rules it is reviewed by; its own `AGENTS.md` changes are reviewed as code. Lockfiles, minified, vendored and generated files leave the diff for `.ai-review.skipped.diff` and are listed at its top, so the one Read the diff gets is spent on code (the prompt says when to read the second file: a lockfile changed without its manifest); a file whose diff runs past 1500 lines is clipped there with a marker and its whole diff goes to that second file too, since the checkout shows neither removed lines nor a deleted file; hunks carry 8 lines of context; grep and glob skip the same files unless called with `include_generated`. It also gets `.ai-review.context`, one file so it costs one Read: the pull request title, description and commit messages, so an intended behavior change is not reported as unintended, and on a later push the previous Claude review of the pull request and the owner's rulings, so a finding that still holds keeps its wording and a rejected one is not raised again in new words, plus the changes since the commit that review saw, so the fixes are checked first. Bash stays off: the job holds the token, and any command has flags that run programs. Since the model reads untrusted code while holding that token, Read is denied the process environment (`/proc`), the runner's credentials and the host's directories, and the verdict text is scrubbed of the token and anything shaped like one before it is posted. If it runs out of turns (`max-turns`, default 100), or ends with the verdict wrapped in a summary of what it checked (Opus did so on 2 of 2 re-runs of one pull request), the same session is resumed with tools off, so it gives its verdict alone, from what it has read, and names the files it did not get to; those files then count as a finding, so the session reviews them itself instead of merging on a verdict that skipped them. Every answer now ends with that `Not reviewed:` line, and a verdict also needs the execution record to show a successful Read of the diff. Each finding ends with the line it points to, quoted; the extraction checks the quote against the checkout, moves the line number when the code moved, and marks a quote it cannot find, never dropping a finding. Each finding also names the test that would fail today, for whoever fixes it: written first, it proves the finding, and one that cannot be made to fail refutes it. The turns, minutes and cost of each review go to the job summary, so `max-turns` and the timeouts rest on data. The resumed answer may add the shape, never drop findings: each finding line of the first answer whose file the resumed answer does not name is carried over as it was, and CLEAN after a FINDINGS that had no finding line gives no verdict. This review is the security gate: a verdict counts only when the execution file shows every answer came from `claude-opus-5-5`, the search server connected and the answer kept to the verdict format, and no verdict is an `error`, never a pass; the answer that gave none is printed in the run log, scrubbed like a posted one. Both reviewers read the pull request, so a hidden instruction in it is a risk to both; what stands between that and a merge is that success needs Codex and Claude to agree, that the verdict must come from the gate model, and that only the owner merges. One known limit: on the persistent dreamfyre review runner, every repository's checkout lives under the same user's home, and Read is bound only by deny rules, so a hidden instruction could have the model read another private repository's files into its verdict. That runner serves only the owner's private repositories and the verdict lands in the owner's private pull request, so the data stays with its owner; a runner user per repository, or a sandbox, would close it. GLM-5.3 held this slot until 2026-10-20; over 54 pull requests it never found a bug that led to a fix. On 8 real bugs Codex had found, run once each at max effort with Read only, Opus 5.5 caught 3 and a P0 nobody else saw, Mythos 5.1 caught 1 and a P1, GLM caught 1, in about the same time; hence Opus.
3. **The coordinator** is plain script logic, not a model. It waits until both have reported on the current head and sets the commit status `ai-review`:

| Status | Meaning | What the Claude session that opened the PR does |
| --- | --- | --- |
| `pending` | reviews are still running | waits |
| `success` | Codex and Claude found nothing | merges and deploys |
| `failure` | findings to rule on | reads Codex's inline comments and the Claude comment, fixes the real ones, pushes; each push is a new round |
| `error` | the pipeline could not finish | stops and reports; when Claude gave no verdict (outage, the subscription's usage window, or a review job cancelled by a timeout or a lost runner while its head was still current), re-runs the whole workflow later with `gh run rerun`. The Claude comment names the cause when the record's API error lines show one: a rejected token (renew it with `claude setup-token` and `enrol.sh`), the usage limit (wait for the window), or an unavailable API (re-run now) |

A finding the session rejects gets a ruling instead of a push. The session replies to each Codex thread and resolves it, then posts one pull request comment that starts with `<!-- ai-review:ruled sha=<full head SHA> -->` and gives its reasons. Neither resolving a thread nor that comment wakes the coordinator, so the session then runs `scripts/recheck.sh <repo> <pr>`, which re-runs it. The re-run uses `review.yml` as it was when that head's run started, because GitHub keeps that SHA when a single job is re-run. The coordinator sets `success` only when all of these hold:

- The comment is the repository owner's.
- It is newer than both reviews' results on that head.
- Codex has finished.
- Every Codex thread is resolved.

A ruling that fails one of these leaves `failure`, and the status says which (`ruling not counted: 1 Codex thread open`, `older than the latest review result`, `Codex security review still running`). The GitHub API calls that post the comment and set the status retry three times, because a dropped call there would leave a stale status that nothing re-runs by itself.

So a finding that lands after the ruling still blocks.

Codex sometimes never reports on a head: it skips a push that lands while it is still reviewing the one before, and a review it starts on a freshly opened pull request can stay `running` forever ([openai/codex#55890](https://github.com/openai/codex/issues/55890), [#57619](https://github.com/openai/codex/issues/57619)). Measured over the 65 heads reviewed between 2026-10-21 and 2026-10-29, every wait over an hour was one of these, and the owner commenting `@codex review` ended each within three minutes. So [`nudge-codex.yml`](.github/workflows/nudge-codex.yml) runs [`scripts/nudge-codex.mjs`](scripts/nudge-codex.mjs) every quarter hour: for each open pull request in the owner's repositories whose `ai-review` status has said `waiting for Codex` for 20 minutes, with no `@codex review` from the owner since the push and no completed Codex review on that head, it posts that comment as the owner. It needs `CODEX_TRIGGER_PAT` in this repository (a fine-grained PAT on all repositories: Issues and Pull requests read and write, Commit statuses read, Actions read), because Codex ignores comments from bot accounts; without the secret it does nothing, and the session comments instead.

With `codex-fixes: true` the coordinator instead asks Codex, using the owner's token because Codex ignores bot accounts, to rule on the findings and push fixes, for up to `max-rounds` rounds. It is off because, as tested on 2026-10-19, Codex cannot push a fix to the pull request branch. GitHub `@codex` fix requests need a Codex Cloud (Legacy) environment for the repository. Without one, Codex asks for it, and a new-style environment alone gets a review instead. With a Legacy environment the task fixes, tests and commits the change, then reports "no configured Git remote or push destination" ([openai/codex#38351](https://github.com/openai/codex/issues/38351)).

## Enrol a repository

From the owner's machine (it needs `gh` and `wsl -e ssh dreamfyre`):

```sh
CLAUDE_TOKEN_FILE=<file> scripts/enrol.sh <repo>
```

The script does four things. Each step is skipped when it is already done, so it is safe to re-run; run again after a change to `caller.yml`, it opens a pull request that updates the caller.

- It sets the secret `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`), which goes from the file straight to `gh`. `CODEX_TRIGGER_PAT` (a fine-grained PAT with Issues and Pull requests read and write) is added only to repositories that turn on `codex-fixes`.
- For a private repository, it registers a review-only dreamfyre runner through the host's root-owned `/usr/local/lib/gha-review/register.sh`. That runner runs as user `gha-review`, separate from the `gha` CI runners, has no Docker, and uses the label `dreamfyre-review`. Public repositories use GitHub-hosted runners, which are free for them; dreamfyre serves private repositories only.
- It opens a pull request that adds [`caller.yml`](caller.yml) as `.github/workflows/ai-review.yml`. The reusable workflow picks the runner from the repository's visibility. `issue_comment` workflows run from the default branch, so until this merges, neither Codex finishing nor a ruling wakes the coordinator after its first run.
- Run again once Codex has reviewed that pull request, and after any ruling, it adds the ruleset [`scripts/ruleset.json`](scripts/ruleset.json) and re-runs the coordinator, so the enrolment pull request also merges on a real `ai-review` success. The ruleset waits for that pull request's run, because it names GitHub Actions as the status source, which GitHub may refuse before Actions has run in the repository. From then on, merging into the default branch needs `ai-review` success, set by GitHub Actions (app 15368), so a status that another account posts does not count. It is a guard against merging too early, not a security boundary. A same-repository pull request that edits a workflow could post that status itself with its own `GITHUB_TOKEN`. Only someone with write access can open one, and in these single-owner repositories that person is an admin who can bypass the ruleset anyway. Claude reviews workflow changes before merge; this repository's own pull requests run the pipeline as it is on `main`. If a repository gains a collaborator with write access, the status has to come from a `workflow_run` on the default branch instead. Fork pull requests cannot post it, because their token is read-only. The ruleset never requires the branch to be up to date, so a merge does not trigger another review. Repository admins can bypass it (`gh pr merge --admin`, or the bypass box in the merge dialog). This is for pull requests that get no status, and for direct pushes. Dependabot pull requests get no status, and neither do fork pull requests, on purpose: the owner merges outside code deliberately. A pull request into another branch gets `error`, because retargeting it to the default branch runs nothing and would otherwise keep a success computed against the old base.

Codex code review must also be enabled for the repository in chatgpt.com/settings/code-review.

The caller tracks `@main`, so a change here reaches every repository at once. That is the point of keeping the logic in one place. The cost is that a push to this repository's `main` runs with those two secrets in every enrolled repository, so treat `main` here like production code.

## Test

```sh
node --test
```

The tests take the coordinator's decision script straight out of `review.yml` and run it against fake GitHub data.
